# Craverly 

A food delivery web app inspired by Zomato/Swiggy — built to go deep on real frontend engineering, not just clone a UI. Live location data, a working cart/checkout flow, real-time-feeling order tracking, and an AI chat assistant, all backed by a generated catalog of ~330 restaurants and ~5,100 menu items across 6 Indian cities.

**🔗 Live demo:**(https://agent-6ab8a6e791bf295--courageous-hamster-cef312.netlify.app/) 

No login or setup needed — it runs fully in local mock mode out of the box. Supabase is optional, only needed for real persistence.

---

## Features

- **Location-aware browsing** — city/area picker scopes home, listings, and search; a "live nearby" strip pulls real open restaurants from OpenStreetMap (Overpass API), cached and throttled, with a catalog fallback if OSM comes up empty
- **Search & filters** — debounced search with autocomplete, voice input, and filters (cuisine, rating, veg/non-veg, price, delivery time) mirrored into the URL so results are shareable
- **Restaurant & menu pages** — customizable menu items (size, spice, add-ons) that price correctly into the cart, allergen/calorie filters, and reviews with photo uploads
- **Cart, checkout & orders** — full cart/checkout flow, saved addresses, coupons, order tracking with a live Leaflet map and a status-timeline simulation engine, order history with reorder, and an analytics dashboard (Recharts)
- **Group ordering** — shareable session code, shared live cart synced via Supabase Realtime, auto bill-splitting
- **Chat assistant** — rule-based intent engine (no external AI key needed) that can actually search, filter, or start checkout from natural language
- **ETA engine** — real delivery estimate from haversine distance + time-of-day traffic + prep/pickup buffers, not a static number
- **Recommendations** — scored from order history, favorites, and recently viewed, with a trending fallback for new users
- Weather-based picks, favorites, dark mode, responsive layout, skeleton loaders, and an error boundary for graceful crash handling
- **Auth** — email/password + Google OAuth, protected routes, works fully in mock mode or against real Supabase

## Tech stack

React 19, TypeScript (strict), Vite 8, Tailwind CSS v4, React Router v7, Zustand (8 stores), Supabase (Postgres/Auth/Storage/Realtime + RLS, optional), Leaflet, Recharts, React Hook Form + Zod, OpenStreetMap (Nominatim + Overpass), Sonner, Lucide React, Vitest + Testing Library, Oxlint, deployed on **Netlify**.

## Architecture

Routes and components never call Supabase directly — everything goes through a service layer in `src/lib/`, which handles the real call and falls back to local mock data automatically. That's what makes the whole app runnable with zero config.

```
src/
  components/   UI by feature (auth, cart, chat, checkout, restaurant...)
  data/         generated catalog, cities, coupons, live-OSM registry
  hooks/        debounce, geolocation, speech, realtime, order simulation
  lib/          service layer — ETA math, weather, chat engine, recommendations
  pages/        one component per route
  store/        8 Zustand stores
  types/        shared domain types
scripts/        deterministic dataset generator
supabase/       SQL migrations, RLS policies, storage setup
```

The catalog is generated by a seeded script (`scripts/generateDataset.mjs`), not hand-typed — same seed, same output every time, which makes it easy to test the UI at real scale.

## Deployment

Live on **Netlify** via `netlify.toml` — build command `npm run build`, publish directory `dist`, Node pinned to v22, and an SPA rewrite so deep links like `/restaurant/42` don't 404 on refresh.

## Testing

```bash
npm test
```

27 tests covering the logic-heavy parts — chat intent detection, ETA calculation, recommendation scoring, and the live-restaurant caching/throttling logic.

This started as a UI clone and turned into - the cart survives a refresh, the map genuinely moves, filtered search results are shareable links, and a stranger can clone the repo and have it running in under a minute with zero setup. 
Most of the interesting problems weren't visual. Getting live restaurant data from a free, keyless API to behave reliably meant building real caching, throttling, and fallback logic instead of just calling fetch and hoping. And keeping eight different pieces of state (cart, filters, location, auth, orders, group sessions, chat, reviews) from stepping on each other pushed me to actually think about state architecture instead of shoving everything into one context.
